## How to Use This Process

### Running the Sync Check Locally

Four complementary checkers guard four different failure modes. **All four must be
green** — each is blind to what the others catch:

**Which spec do they read?** CI is **hermetic**: it passes
`--spec-file .github/cache/samsara-api-baseline.json`, so the checkers measure the SDK
against the spec it has actually been reconciled against. An upstream edit can then never
turn an unrelated PR red — and, more importantly, live-vs-SDK checks previously *masked* a
stale baseline. Watching the live spec is the daily `api-sync-check` workflow's job, and
its only job.

```bash
SPEC=.github/cache/samsara-api-baseline.json

# 1. SPEC DRIFT — does the live spec differ from our cached baseline?
#    Omit --spec-file to fetch live. --no-report keeps the working tree clean.
python3 tools/check-api-sync.py --no-report --summary-json /tmp/drift.json

# 2. COVERAGE — does every SDK path exist in the spec, and is every spec op implemented?
python3 tools/check-sdk-sync.py --spec-file "$SPEC" --fail-on-mismatch --fail-on-unimplemented

# 3. FABRICATION / MIS-HOMING — does every SDK method map to a DISTINCT, correctly-homed
#    spec op? Catches the Hubs-class bug (a method pointed at another domain's path, e.g.
#    HubsClient CRUD secretly hitting /addresses) that COVERAGE reports as "0 mismatches".
python3 tools/check-sdk-fabrication.py --spec-file "$SPEC" --fail-on-issues

# 4. MODEL PARITY — do SDK record *shapes* match the spec request/response bodies,
#    property by property (matched by endpoint, not by type name)?
python3 tools/check-model-sync.py --spec-file "$SPEC" --fail-on-severity MEDIUM

# 5. Regenerate the README status block after any of the above changes.
python3 tools/render-sync-status.py --write
```

> **Both gates are now ON.** The v0.5.0 sweep finished the backlog they measure, so
> `ci.yml` runs #2 with `--fail-on-unimplemented` and #4 at `--fail-on-severity MEDIUM` —
> the commands above are exactly what CI runs. A newly unimplemented spec operation, or any
> MEDIUM model finding (weak typing, flattened records, type or required-ness drift), fails
> the build rather than being counted in a status block nobody reads.
>
> Three `LOW` weak-typing findings remain active and deliberately **un-allowlisted**:
> `FunctionRunContext.requestPayload` / `.responsePayload` and `ReportRunData.rows`. The
> spec leaves all three genuinely free-form, so they sit below the gate and stay visible.

Why four? Each catches what the previous is structurally blind to:
- `check-sdk-sync.py` dedups SDK endpoints by `(verb, path)`, so a method mis-homed to a
  *real* path in another domain is counted as coverage and never flagged.
- `check-sdk-fabrication.py` adds the reverse check: **duplicate coverage** (one spec op
  reached from >1 client file) and **client↔tag drift** (a method reaching a spec tag outside
  its client's committed allow-set in `tools/sdk-client-tags.json`). After an intentional new
  cross-domain method, refresh the allow-set with `--update-tags` and review the diff.
- `check-model-sync.py` goes one level deeper than paths: it compares the C# record
  *properties* the SDK sends/receives against the spec schema the endpoint actually
  uses (unwrapping the `{ data: … }` envelope). It is what keeps models from silently
  rotting as the spec mutates. CRITICAL = wrapper-shape mismatch; HIGH = missing/required
  drift on a required field or required query param; **MEDIUM gates** and covers
  `missing-optional`, `type-mismatch`, `weak-typing` (a weak C# type — `object`,
  `JsonElement`, or a collection of them — where the spec defines a *concrete* schema), and
  `flattened` (a nested spec object collapsed onto its parent record). Beta endpoints are
  capped at MEDIUM, which now only prevents a CRITICAL/HIGH *label*; it no longer exempts
  anything from the gate.

**On the allowlist.** `check-model-sync.py` has an `ALLOWLIST` of documented, intentional
deviations. Every `weak-typing` entry must cite the **spec pointer** proving the schema is
genuinely free-form (e.g. `{type: object}` with no `properties`), and blanket or wildcard
keys are forbidden. This rule exists because a single blanket entry —
`("object", "*", "weak-typing")` — collapsed 94 weakly-typed endpoint bodies into one
accepted line and hid the entire backlog while the checker reported green. Adding an
allowlist entry to make a build pass is the failure mode this tooling exists to prevent.

### Spec-drift detection & baseline discipline

Samsara ships spec changes **without bumping `info.version`** — the live spec has been
`2025-10-23` for months while its content (schemas, fields, descriptions) keeps moving. So
`check-api-sync.py` does not trust the version string:

- It diffs the live spec against the cached baseline (`.github/cache/samsara-api-baseline.json`)
  at three levels: **endpoints** (added/removed/changed operations & params), **schemas by name**
  (added/removed), and **schema properties** (fields and `required`-set added/removed on schemas
  present in both — the model-drift signal a name-only diff misses).
- It prints a **content fingerprint** (op count, schema count, short content hash). When the hash
  moves but the version string doesn't, the report flags *"⚠️ Spec content changed under the same
  `info.version`"* so a cosmetic-looking "no version change" can't hide real drift.

**Drift classification.** `check-api-sync.py --summary-json` labels every diff exactly one of:

| Class | Meaning | Who absorbs it |
|---|---|---|
| `none` | identical content hash | nobody |
| `cosmetic` | hash moved, but **zero** endpoint deltas and **zero** schema property/required deltas — i.e. summary/description/example churn | the daily workflow, automatically |
| `structural` | any operation added/removed/changed, deprecation flip, schema added/removed, or property/required delta | a human or agent, in an implementation PR |

Endpoint `summary` text is deliberately excluded from `structural` and tracked separately as
`summary_only`: prose edits are not contract changes, and treating them as such would have
every run demand attention.

**Baseline-refresh discipline** — the baseline is the spec the SDK has been reconciled
against, so it advances alongside reconciled code and (with one narrow exception) never on
its own:

1. **Cosmetic drift is absorbed automatically.** The daily workflow runs `--update-baseline`
   and pushes a `chore(api-sync): refresh baseline (cosmetic drift …)` commit to `main`. By
   definition this changes no contract. Every such move is auditable with
   `git log -- .github/cache/`.
2. **Structural drift is never auto-absorbed.** It opens an `api-sync` issue containing a
   complete implementation spec. The baseline is refreshed **inside the implementation PR,
   as its first commit** — the baseline diff in that PR *is* the reviewable spec change.
3. Locally, never run `--update-baseline` on `main` outside that PR. Refreshing before
   reconciling silently swallows the drift and makes the next diff lie.
4. After reconciling, all four checkers must be green against the refreshed baseline, and
   `tools/render-sync-status.py --write` must be re-run.

### Updating Checklists After Implementation

When implementing an endpoint, update its checklist file by checking off the relevant items:

```markdown
- [x] Method defined in `IFooClient`
- [x] Method implemented in `FooClient.cs`
- [x] Request model(s) defined (if applicable)
- [x] Response model(s) defined
- [x] JSON serialization context updated (`SamsaraJsonContext.cs`)
- [ ] Unit/integration test coverage
```

Also update the status line at the top of the file and the table in this README.

### Adding a New Domain

1. Identify the API tag(s) that map to the new domain
2. Create `I<Domain>Client.cs` interface
3. Create `<Domain>Client.cs` implementation
4. Create `Models/<Domain>/<Domain>Models.cs`
5. Register in `ISamsaraClient` and `SamsaraClient`
6. Register in `SamsaraJsonContext.cs`
7. Create or update the checklist file in `docs/api-sync/`
8. Update this README index table

### Daily Automated Check

`.github/workflows/api-sync-check.yml` runs every day at 06:00 UTC (plus
`workflow_dispatch`):

1. Fetches the live spec **once** and diffs it against the committed baseline.
2. Classifies the drift as `none` / `cosmetic` / `structural` (see the table above).
3. **Cosmetic** → refreshes the baseline and pushes a bot commit to `main`. No issue.
4. **Structural** → runs all three SDK checkers against the live spec, renders a full
   report, and creates (or updates in place) the single open `api-sync` issue. The body is
   a **complete implementation spec**: the endpoint diff, the unimplemented operations, SDK
   mismatches, model findings, and the exact steps and commands to close it.
5. Uploads the full report as a 90-day run artifact.

The issue is written so it can be **assigned directly to the Copilot coding agent**, or
handed to a local agent, with no extra context. A hidden `<!-- api-sync-fp:<hash> -->`
marker means an unchanged live spec never re-posts the same drift.

`workflow_dispatch` inputs: `dry_run` (run every check but write nothing) and `force_issue`
(open the issue even when drift is only cosmetic).

**Repo setup this depends on:** the `api-sync` label; Actions "Read and write permissions";
and — to make green mean compliant — a ruleset on `main` requiring the `sdk-sync` status
check, with a bypass for the `github-actions` app so the cosmetic baseline commit can push.
If app bypass is not permitted, switch the cosmetic path to an auto-merged PR (requires
`allow_auto_merge`).

## Versioning

The Samsara API version is embedded in the spec's `info.version` field — but **do not rely
on it**. Samsara has shipped months of content changes under a frozen `2025-10-23`, so the
content hash, not the version string, is the drift signal. Issue titles cover both cases:
`[api-sync] Samsara API updated: 2025-10-23 → 2026-04-01` for a real bump, and
`[api-sync] Samsara spec drift (2025-10-23, content abc → def)` for in-place mutation.

After implementing changes for new spec content, update:
1. The generated status block — `python3 tools/render-sync-status.py --write`
2. Each affected checklist file's status
3. `CHANGELOG.md` with a new entry describing the changes

## File Structure

```
docs/api-sync/
├── README.md                     ← This file (index + process guide)
├── spec-parity-plan-2026-08-17.md ← v0.5.0 full-parity plan (endpoints, typing, tooling)
├── 01-addresses.md
├── 02-alerts.md
├── ...
└── 56-work-orders.md
```

`diff-report.md` is **not** tracked (it is generated; see `.gitignore`). Drift reports live
in the workflow run artifact and the `api-sync` issue.

Tooling:

```
tools/
├── check-api-sync.py         ← live/local spec vs committed baseline; drift classification
├── check-sdk-sync.py         ← every SDK path is a real spec op; every spec op implemented
├── check-sdk-fabrication.py  ← duplicate coverage + client↔tag drift (mis-homing)
├── check-model-sync.py       ← record properties vs the schema the endpoint actually uses
├── render-drift-report.py    ← checker JSON → drift report + api-sync issue body
├── render-sync-status.py     ← generates the status block above (--write / --check)
└── sdk-client-tags.json      ← committed client→spec-tag allow-set
```

Each checklist file follows this structure:
- **Header** — API version, status, SDK client mappings
- **Endpoints** — Per-endpoint checklist (interface, impl, models, serialization, tests)
- **Models** — Domain model quality checklist
- **Notes** — Implementation notes, breaking changes, special considerations
